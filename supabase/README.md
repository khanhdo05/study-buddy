# Supabase setup

This folder owns the shared database migrations and access policies. The React frontend uses Supabase Auth and the Data API; AI processing remains backend work.

## Apply the first migration

1. Open your Supabase project's **SQL Editor**.
2. Create a new query, paste the contents of `migrations/202609180001_auth_and_courses.sql`, and run it once.
3. Confirm that the query succeeds before testing sign-up. It creates profiles automatically when accounts are created and backfills existing accounts.

This migration targets a new project with no conflicting `profiles`, `courses`, `enrollments`, `course_invitations`, or bucket names. It runs in a transaction. If your project already has those objects, inspect and reconcile the schemas first; do not drop existing data to make it run.

Subsequent schema changes should be new migration files committed with their feature changes. Do not edit an already-applied migration. When the team adopts the Supabase CLI, use its migration workflow and reconcile this first migration's history if it was applied through the dashboard.

## Authentication configuration

In **Authentication → Providers**, enable email/password sign-in. Keep email confirmation enabled.

In **Authentication → URL Configuration**, use `http://localhost:5173` as the development Site URL and allow these redirect URLs:

- `http://localhost:5173/`
- `http://localhost:5173/?auth=recovery`

If using `127.0.0.1`, another port, or a deployed frontend, add its exact URLs too. Configure production Site URL and redirects before deploying. Restart Vite after changing `.env.local`.

For team testing with real email addresses, configure your own SMTP provider in Supabase. The default email service has recipient and rate restrictions; a successful frontend build does not verify email delivery.

## Frontend configuration

Copy `react-frontend/.env.example` to `react-frontend/.env.local` and fill in the project URL and **publishable** key. The publishable key is intended for the browser; database policies enforce access. Never use a secret or service-role key in frontend code or `VITE_*` variables.

## Access model

- Profiles: users read their own profile and may update only their name.
- Roles: a sign-up choice is copied once into the profile. This MVP permits self-selected professors to create their own courses. It is not institutional verification. Later metadata changes cannot promote a student.
- Courses: only owners and enrolled students can read them; only professor owners can modify them.
- Enrollments: created only through the invitation RPC. Users cannot insert memberships directly.
- Invitations: generated by owners, stored hashed, expire after seven days, reusable by multiple students, and replaced when a new code is generated.
- Storage: both buckets are private. Paths must be `<course UUID>/<filename>`. Course-material files can be read by the owner and enrolled students. Professor-material files can be read only by the owner. Only owners can write files.
- Both buckets allow PDF, plain text, and PPTX files up to 25 MiB. An upload interface and processing pipeline are not included yet.

The helpers in the `private` schema must remain outside the Data API's exposed schemas. No secret key is required for frontend account/course operations.

## Verification

`tests/access_control.sql` runs transactional assertions for owner/student isolation, unauthorized writes, enrollment bypass, invitation expiry, role tampering, and file visibility. It rolls back its test data. Use a disposable test environment.

For a bare PostgreSQL database, `tests/local_fixture.sql` provides minimal Supabase schema stand-ins. **Never run that fixture on a Supabase project or an existing database.** In a fresh disposable PostgreSQL cluster:

```bash
psql "$TEST_DATABASE_URL" -v ON_ERROR_STOP=1 \
  -f supabase/tests/local_fixture.sql \
  -f supabase/migrations/202609180001_auth_and_courses.sql \
  -f supabase/tests/access_control.sql
```

The fixture verifies SQL and row-level access behavior, not Supabase Auth token handling, email delivery, or actual file transfer. Verify those on a configured Supabase test project.

## Manual end-to-end checks

1. Sign up as a professor, confirm email, sign in, and create a course.
2. Open that course, select **Course settings**, and generate an invitation code.
3. Sign out, sign up as a student with a different email, and join using the code.
4. Refresh inside the course workspace: the student should remain in the selected course view. Try browser Back and returning to My courses. Sign out and back in to confirm persistence.
5. A second student must not see the course until joining; a second professor must not see or manage it.
6. Request a password reset and use the emailed link to set a new password.
7. Open the sample course: its scripted chat and device-local progress must remain clearly separate from account data.

Real-course quiz generation, evaluated results, persistent concept state, chat, and material uploads are future work. Do not store mastery scores supplied directly by the browser as authoritative results.
